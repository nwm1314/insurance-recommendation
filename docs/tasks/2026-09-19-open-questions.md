## OPEN-001：是否引入真实投保跳转 / 留资能力

- **背景与证据**：
  - 用户填完 4 步问卷能拿到三套方案，但结果页**没有可执行的下一步动作**。产品链接（`ProductItem.source_url`）仅跳转到外部来源页（聚合站产品详情页或保险公司官网）。
  - `README.md:278` 明确："系统不提供实时核保或保险公司报价 API，保费区间、健康匹配和保额均为辅助信息，最终以保险公司官方条款、健康告知和核保结果为准。"
  - 上一轮会话的探测脚本 `frontend/_shots.cjs:48` 曾显式检查结果页是否存在 `/立即投保|去投保|购买|咨询/` 类动作，说明该问题此前已被注意到。
  - 本项属评审提示词 §5.1 明确点名的问题："用户的下一步动作是什么（跳转投保页 / 咨询 / 留资）——目前是否断链？"
- **可选方案（含各自代价）**：
  1. **维持现状（纯展示 + 外链）**：零合规风险、零开发成本；代价是转化链路断链，用户价值停留在"知道该买什么"。
  2. **保留资/咨询入口（站内表单）**：可形成转化闭环；代价是**触发个人信息采集合规要求**（需告知—同意、留存策略、去标识化），且需明确"非承保承诺"表述。
  3. **跳转保险公司官网投保页**：体验最直接；代价是需要校验并维护各产品的真实投保直链（当前多数为聚合站产品页，非投保页），存在链接失效与"未披露上限"产品的合规标注问题。
  4. **引入第三方经代/联盟合作**：商业模式清晰；代价是引入外部依赖与结算链路，超出本期"可对外内测"范围。
- **我的建议与理由**：
  建议**本期先做方案 1 + 局部增强**：保留外链但补强"下一步说明"文案（明确告知当前为辅助决策工具、投保需前往官方渠道并以其核保结论为准），把方案 2/3 作为内测后迭代项。理由：方案 2/3 都会引入新的个人信息采集面或外部链接维护成本，与提示词"不得暗示承保保证""不新增中间件"的约束张力较大，且缺少法务输入时不宜自行定案。
- **需要谁决定**：产品负责人（若涉及留资/经代合作，需法务共同确认）。

## OPEN-002：健康信息明文落库是否允许进入对外内测

- **背景与证据**：
  - 本地/E2E 环境启动实测告警：`RECORD_ENCRYPTION_KEY is not set: recommendation records (profile/result, including health disclosures) will be stored in PLAINTEXT.`
  - 推荐记录含健康告知（`health_status`、`health_issues`，后者为 70+ 健康编码），属敏感个人信息。
  - 该明文行为是**既定 fail-open 设计**（未配置密钥时保证本地可用），并非缺陷；`test_ops002_security.py` 已覆盖加密路径。
- **可选方案（含各自代价）**：
  1. **内测即强制配置密钥**：合规风险最低；代价是本地/CI 需注入密钥，已有明文历史记录需处理（无法回读或需迁移）。
  2. **允许内测沿用明文，仅在正式对外前配置**：开发体验最好；代价是内测期间产生的真实健康数据以明文留存。
  3. **本地明文 + 内测环境强制密钥（分环境门禁）**：兼顾开发体验与合规；代价是需在部署清单中明确为硬性前置检查，并防止误配。
- **我的建议与理由**：建议方案 3。保留本地 fail-open（不破坏开发与既有测试），但把"内测/生产必须配置 `RECORD_ENCRYPTION_KEY`"写成部署清单的**硬性卡点**。理由：`PROD-002` 卡已按此方向实现文档与门禁增强，不需要改运行时语义。
- **需要谁决定**：产品负责人 + 运维/部署负责人（涉及数据合规，建议法务知会）。

## OPEN-003：三套套餐命名是否会让普通用户误以为"贵的更好"

- **背景与证据**：
  - 结果页三套套餐命名沿用"极致性价比 / 全面保障 / 尊享无忧"（评审提示词 §6.3 点名项）。
  - 本次评审**未取证**该命名对用户决策的实际影响（无用户测试），故不构成"已证实问题"，仅登记待决策。
- **可选方案（含各自代价）**：
  1. **维持现名**：用户熟悉、文案稳定；代价是"尊享"字面暗示更优，可能诱导超预算选择。
  2. **改为中性功能化命名**（如"低保费优先 / 均衡 / 高保额优先"）：降低诱导性、更贴合引擎真实逻辑（预算占比与保额取向）；代价是文案需全局替换并同步 README，且需重新取得 UI 证据。
  3. **保留现名但补一行副标题说明差异**：改动最小；代价是首屏信息密度增加，与"减少认知负担"原则有张力。
- **我的建议与理由**：倾向方案 2，但**建议先做小样本用户测试再定**。理由：命名属纯产品判断，缺乏用户证据时改与不改都有风险；若必须立即决定，方案 2 更符合提示词 §4"不得暗示承保保证/夸大"的取向（"尊享"隐含优劣暗示）。
- **需要谁决定**：产品负责人（建议结合设计走查结论）。

- **背景与证据**：
  - `ProductItem` 类型已定义 `last_verified_at` 与 `data_stale`（`frontend/src/types/index.ts:61-62`，注释"超过 90 天未复核"）。
  - 本次评审**未构造超 90 天未复核产品**做实测，故"标注是否真的触发"**未复现**（已列入评审报告 §4 待验证假设）。
  - `SEED_DEMO_PRODUCTS` 默认 false 已确认，真实/演示数据边界清晰。
- **可选方案（含各自代价）**：
  1. **本期补实测并闭环**：结论可靠；代价是需要构造测试数据，占用一轮修复额度。

- **我的建议与理由**：建议方案 1（低成本、可自动化，作为 `PROD-003` 卡执行）。理由：该字段直接影响"决策可信度"这一产品承诺，且构造测试数据成本不高，无需人类输入即可完成——除非决定不做，才需要拍板。

## OPEN-005：是否允许为满足"测试隔离"新增 `backend/tests/conftest.py`

- **背景与证据**：
  - 批次 A（DEV-001/002）计划新增 `backend/tests/conftest.py`，为全量后端测试注入隔离 Redis（沿用既有 `StubRedis` 模式）。
  - 提示词 §7 禁止"不新增依赖"；**本方案不新增任何依赖**，仅新增一个测试内文件。
  - 但该文件会影响**全部 24 个测试文件**的运行时行为，属跨文件改动，故在此登记确认。
- **可选方案（含各自代价）**：
  1. **新增共享 `conftest.py` 统一隔离**（推荐）：一处生效、后续测试天然免疫；代价是影响面大，需验证不破坏既有 280 条用例。
  2. **逐文件添加隔离 fixture**：影响面可控、易回滚；代价是重复代码，且未来新增测试文件仍会踩坑。
  3. **测试改用独立 Redis DB index / 独立实例**：隔离最彻底；代价是需要环境配置支持，CI 需同步调整，超出"不新增中间件"边界。
- **我的建议与理由**：建议方案 1。理由：这是根因修复而非症状掩盖，符合提示词"先复现再修"与"不做范围外重构"的平衡；若验证中发现破坏既有用例，则回退到方案 2。
- **需要谁决定**：技术负责人（若默认采纳建议则无需阻塞执行）。
